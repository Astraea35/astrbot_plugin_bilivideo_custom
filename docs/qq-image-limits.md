# QQ 合并转发图片边界实测

测试日期：2026-10-22。运行环境：NapCat 4.18.41、QQ 3.2.28-48517，非 packet 合并转发路径。

未在 QQ/NapCat 公开文档中找到适用于所有客户端和账号的统一像素上限。以下是当前环境的实测结果，不能视为官方承诺。

## 单边边界

使用同一张总结图生成 PNG 对照，通过机器人自聊发送，不向用户或群投递；每次检查发送返回值。固定宽 2640，从高度 8000、16000、24000、32000 开始，再二分查找相邻像素边界。

| 尺寸（宽 × 高） | 总像素 | 结果 |
| --- | ---: | --- |
| 2640 × 29999 | 79,197,360 | 成功 |
| 2640 × 30000 | 79,200,000 | 失败，1200 / rich media transfer failed |
| 660 × 30000 | 19,800,000 | 失败，1200 / rich media transfer failed |
| 29999 × 660 | 19,799,340 | 成功 |
| 30000 × 660 | 19,800,000 | 失败，1200 / sendMsg 超时 |
| 8000 × 8000 | 64,000,000 | 成功 |
| 10000 × 10000 | 100,000,000 | 成功 |

在本次环境中，宽、高均需要小于 30000 像素。总像素达到一亿仍能发送，说明此次故障不是简单的 2000 万或 6400 万总像素上限；没有继续用更大图片探测总像素极限。

原事故图片 2640 × 34420 发送失败，缩小到 660 × 8605 后成功。将缩小图填充至与原图完全相同的 4,218,233 字节仍成功；保留原尺寸的较小 JPEG 仍失败，排除了单纯文件体积这一解释。

## 合并转发会静默少节点

输入 2 个节点（文字通知、带图片的总结），回读 `get_msg` / `get_forward_msg`：

- 29999 像素高的图片最终回读为 2 个节点；首次回读可能暂为空。
- 30000 像素高的图片最终只有 1 个文字节点，但发送接口仍返回 `status=ok / retcode=0`。

同版本源码的非 packet 路径会捕获节点发送失败并继续生成其余转发节点：

- [NapCat 4.18.41 SendMsg.ts](https://github.com/NapNeko/NapCatQQ/blob/v4.18.41/packages/napcat-onebot/action/msg/SendMsg.ts#L420-L434)
- [NapCat API 文档](https://napneko.github.io/onebot/api)

因此插件不能仅凭发送调用没有异常就把订阅标记为已投递。

## 插件采用的余量

- 每张输出图片单边不超过 28000 像素，总像素不超过 64,000,000；这是兼顾传输和内存的保守输出限制，不是 QQ 总像素上限。
- 通过浏览器的实际页面高度和缩放倍率计算分片，优先选择段落边界；无法找到边界时重复一行，避免截断文字。
- 章节拆分开关不覆盖像素安全分图。
- QQ 合并转发经已配置的 AstrBot OneBot 客户端发送，并回读节点数和图片数量；首次回读暂为空时短暂重查，不重复发送。
- 校验失败的订阅保留原 `last_bvid`，下次检查重试；普通手动总结可回退到独立图片/文字。

客户端、协议端或服务策略变化后应重新测试；平台接口暂不可用时，保留未确认状态，不声称已经完整投递。

## 修复后验证

用修复代码重新渲染原视频的同一份缓存总结，关闭章节分页，得到 2640 × 24238、2640 × 7982 两张图片。经插件实际发送校验函数向机器人自聊发送后，5 个节点全部回读成功；同一校验函数对旧长图准确报告“预期 4 条、回读 3 条”，没有把不完整转发判断为成功。

相关 64 项回归测试全部通过。全量测试为 294 项，其中 272 项通过、22 项失败；修改前基线为 280 项、23 项失败，对照没有新增失败。全仓 Ruff、mypy 仍存在历史诊断，本次与基线对照没有新增诊断。
